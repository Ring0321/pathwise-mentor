# 自适应学习伙伴智能体设计方案 v0.1

项目暂名：SE-Path 学伴  
赛题方向：面向特定学科专业的自适应学习伙伴智能体  
学科场景：软件工程项目制学习  
当前状态：重新开题，旧 PR/CI 单点 Demo 方向作废

---

## 0. 方向重置说明

这次不再沿用前面的页面和 Demo 主线。

旧方向的问题：

1. 过度围绕“PR/CI 失败工单”展开，像一个软件工程助教工具，不像完整的“自适应学习伙伴智能体”。
2. 页面上堆了太多参赛验收、证据账本、评委导览模块，产品感被比赛材料感压住。
3. 闭环更多是“演示跑通”，但学生真实学习过程中的诊断、规划、陪伴、反思和长期记忆没有成为主体验。
4. 创新点散在 SafeVOI、证据链、教师门禁等模块里，但没有形成一个清晰的产品范式。

新方向的核心判断：

不要做“某一次作业失败后的补救工具”，而要做“软件工程学习全过程的个人成长伙伴”。  
产品应该像一个会陪学生做项目、会看懂学习证据、会动态调路径、会提醒反思、会把成长交给老师复核的智能体。

更进一步，本项目应把“增值性教育评价”作为底层发动机，而不是答辩材料里的一个评价模块。  
系统的核心问题不是“学生现在得了多少分”，而是“在给定起点、阶段、任务和证据条件下，学生是否比自己的合理预期轨迹成长得更好；如果没有，下一步哪种行动最能带来新的学习增值证据”。

保留的底层思想：

1. AI 只做候选建议，不替学生完成高风险结果。
2. 所有诊断和路径调整都要有证据来源。
3. 学习路径不是静态课程表，而是随学生行为持续更新。
4. 老师不是被 AI 替代，而是拥有复核、配置和干预权。
5. 增值评价只做诊断与改进，不做学生排名、单一标签或高利害自动决策。
6. 学生成长增值 VA 与平台服务效益 SE 必须拆开表达，不能把学生自身努力直接归因给系统。

废弃的主线：

1. “把一次失败 PR 变成工单”不再作为产品主线。
2. “评委验收包、提交收口链”不再放在产品核心页面。
3. “大量模块展示型后台”不再作为第一版形态。

## 1. 新选题定义

### 1.1 一句话定义

SE-Path 学伴是一款面向软件工程项目制课程的自适应学习伙伴智能体，能够根据学生的知识掌握、项目行为、代码实践、学习对话和反思记录，持续诊断学习状态，生成个性化成长路径，并以脚手架式陪伴帮助学生完成从“会做题”到“会做项目”的能力迁移。

### 1.2 不是做什么

不是普通 AI 聊天答疑工具。  
不是自动写代码工具。  
不是单纯的刷题推荐系统。  
不是只给老师看的教学数据看板。  
不是为了比赛展示而拼接模块的 Demo。

### 1.3 真正要做什么

做一个“学生每天真的会打开”的学习伙伴：

1. 今天我该学什么。
2. 我为什么卡住。
3. 下一步我该怎么做。
4. 我能不能请求提示，但不被直接喂答案。
5. 我做完之后，系统能不能记住我的成长。
6. 老师能不能看见我真实的努力和短板。

## 2. 赛题要求对齐

赛题要求的核心能力可以拆成四项：

1. 学情诊断：通过对话或测试动态分析学生知识掌握情况，构建学生画像。
2. 路径规划：基于学生画像和知识图谱，动态生成个性化学习路径。
3. 实时干预：学生遇到困难时，提供脚手架式辅导，而不是直接给答案。
4. 记忆与反思：智能体具备长期记忆，多次交互中持续优化学习计划。

SE-Path 的对应设计：

| 赛题能力 | 本项目实现 | 创新表达 |
|---|---|---|
| 学情诊断 | 学习数字孪生，融合测验、项目、代码、对话、反思证据 | 不只看分数，而是看学习过程 |
| 路径规划 | 能力图谱 + 项目里程碑 + 动态路径引擎 | 把课程路径变成可调整的成长路线 |
| 实时干预 | Socratic 脚手架、错误定位、概念回补、任务拆解 | 帮学生迈下一步，不替学生走完 |
| 记忆反思 | 长期学习记忆、反思卡、迁移任务、成长证据 | 每次项目经历沉淀成下一次学习策略 |

## 3. 目标用户

### 3.1 学生

典型用户：软件工程、计算机科学、人工智能、电子信息等专业学生。

学生痛点：

1. 学过很多概念，但做项目时不知道怎么用。
2. 遇到 Bug 时只想要答案，缺少系统化定位方法。
3. 不知道自己到底是概念不会、设计不会、测试不会，还是工程习惯不好。
4. 老师反馈滞后，项目做完才知道问题很大。
5. 学习过程没有被记录，努力和成长难以证明。

学生需要：

1. 一个能看懂自己项目状态的伙伴。
2. 一个能提醒“下一步”的路径助手。
3. 一个不会直接替写、但能把问题拆开的教练。
4. 一个能记录长期成长的学习档案。

### 3.2 教师

教师痛点：

1. 班级项目制教学中，每个学生问题不同，人工逐个跟进成本高。
2. 很多学生最后只提交结果，过程不可见。
3. AI 工具容易替写，教师难判断学生真实能力。
4. 课堂教学调整缺少细粒度证据。

教师需要：

1. 快速知道哪些学生需要干预。
2. 看见学生的证据链，而不是只看最终作业。
3. 配置课程 Rubric、能力图谱和 AI 边界。
4. 对高风险提示进行复核。

### 3.3 教学管理者

关注点：

1. 课程是否真的提升学生能力。
2. AI 是否可管可控。
3. 数据是否合规。
4. 系统是否能推广到更多课程。

## 4. 产品愿景

### 4.1 产品定位

SE-Path 学伴 = 学生端智能学习伙伴 + 教师端 GrowthOps 工作台 + 课程端能力图谱引擎。

### 4.2 产品主张

让软件工程学习从“交作业后评价”变成“项目过程中持续陪伴、持续诊断、持续增值”。

### 4.3 一等奖级别的表达

普通方案说：我们用大模型给学生答疑。  
SE-Path 说：我们让每一次项目行为都成为学习证据，让每一次 AI 帮助都受教育边界约束，让每一次路径调整都能被教师复核和长期记忆。

## 5. 核心创新

### 5.0 总创新：增值性教育评价驱动的学习伙伴

新方案必须把“增值性教育评价”放在产品中心。

传统学习产品通常回答三个问题：

1. 学生现在会不会。
2. 下一节课推荐什么。
3. 作业最后有没有完成。

SE-Path 要回答的是更高级的问题：

1. 学生相对于自己的起点有没有成长。
2. 哪个能力维度产生了成长。
3. 哪些成长由真实学习证据支持。
4. 哪些只是过程活跃，不应被当作能力提升。
5. 哪些系统干预可能有效，哪些必须等真实试点后才能声明。

因此，产品的主引擎应从“路径推荐引擎”升级为：

> 学习增值路径引擎 = 学习数字孪生 + 能力图谱 + 成长基线 + 路径行动实验 + 脚手架干预 + 教师复核 + 增值证据账本

它不是给学生一个静态分数，而是持续计算：

> 学习增值 VA = 当前阶段实际能力准备度 - 基于起点、阶段、任务和参照群体预测的应有准备度

第一版不需要直接做复杂因果模型，但必须在产品结构上预留：

1. 起点基线。
2. 阶段性测量。
3. 可比参照。
4. 成长区间。
5. 证据来源。
6. 不确定性说明。
7. 教师复核。

这会让 SE-Path 和普通 AI 学习助手拉开差距：普通助手只会“回答问题”，SE-Path 能解释“学生为什么成长、哪里没成长、下一步怎样产生可验证成长”。

### 5.1 创新一：学习数字孪生 Learner Twin

不是简单学生画像，而是持续更新的学习数字孪生。

它包含：

1. 知识掌握：概念、方法、工具、工程规范。
2. 项目能力：需求分析、设计建模、编码实现、测试验证、协作交付。
3. 学习行为：求助方式、调试路径、提交节奏、反思质量。
4. 风险状态：替写倾向、浅层完成、卡点累积、知识断层。
5. 成长证据：每一次成功迁移、每一次修正、每一次反思。

关键价值：

学生看到的是“我现在处在哪个成长位置”。  
老师看到的是“这个学生为什么卡住”。  
系统看到的是“下一步干预能带来什么学习增值”。

增值评价嵌入方式：

1. 每个画像节点都保存起点值、当前值、预期值和证据置信度。
2. 不把学生与全班粗暴排名，而是与自己的历史轨迹和可比起点学生比较。
3. 如果证据不足或区间过宽，系统输出“不确定，需要补证”，而不是强行判断“有进步/没进步”。

### 5.2 创新二：能力图谱 + 项目图谱双图谱

普通知识图谱只描述知识点关系。  
SE-Path 设计“双图谱”：

1. 能力图谱：软件工程课程能力节点。
2. 项目图谱：真实项目任务、产物、流程和协作节点。

示例：

能力节点：

1. 需求理解
2. 用例建模
3. API 设计
4. 数据模型
5. 异常处理
6. 单元测试
7. 集成测试
8. 代码评审
9. 版本协作
10. 交付反思

项目节点：

1. 需求卡片
2. 接口文档
3. 数据表设计
4. 功能分支
5. Pull Request
6. 测试报告
7. 迭代复盘

创新点：

系统不是问“这个知识点你会不会”，而是判断“你能不能在项目节点里调用这个能力”。

### 5.3 创新三：路径增值引擎 Path Value Engine

路径规划不只是推荐下一节课，而是计算“下一步最值得做什么”。

每个候选学习行动都计算：

1. 学习收益：能补哪个能力短板。
2. 信息增益：做完后能更清楚判断什么。
3. 迁移价值：能否迁移到后续项目。
4. 时间成本：学生当前是否承受得住。
5. 风险成本：是否可能变成替写或依赖。
6. 教师可控性：是否需要教师确认。

输出不是一句“建议学习测试”，而是一条有理由的学习路径：

下一步：补一个失败测试。  
原因：当前最大短板是边界条件建模。  
证据：接口异常日志、Rubric、学生提问。  
限制：不提供完整实现代码。  
完成标准：学生能解释失败原因并提交最小修复。

这里的“增值”不是营销词，而是路径行动的选择标准：

1. 优先选择能带来能力成长的行动。
2. 优先选择能暴露真实卡点的行动。
3. 优先选择能形成可复核证据的行动。
4. 阻断高负担、低信息、不可逆或可能诱导替写的行动。

### 5.4 创新四：脚手架式伴学，而非答案式答疑

系统的提示分四层：

1. 定位层：帮学生找到问题在哪里。
2. 提问层：用问题引导学生自己说出原因。
3. 结构层：给检查清单、步骤和边界。
4. 验证层：让学生用测试、解释或反思证明掌握。

禁止直接输出：

1. 完整作业答案。
2. 可复制提交的完整代码。
3. 绕过课程规则的提示。
4. 替学生做最终判断的高风险结论。

### 5.5 创新五：教师可控的 AI 学习边界

每条 AI 建议都有状态：

1. 自动可发：低风险提示。
2. 需教师抽查：中风险建议。
3. 必须教师复核：涉及替写、评分、项目关键决策。

这让产品更适合真实学校，而不是只适合演示。

### 5.6 创新六：长期记忆与成长证据账本

系统记录的不是聊天历史，而是学习成长事件。

每条记忆包括：

1. 卡点是什么。
2. 证据来自哪里。
3. 系统给了什么脚手架。
4. 学生做了什么。
5. 老师是否确认。
6. 下次遇到类似任务时怎么迁移。

长期价值：

1. 学生形成个人成长档案。
2. 老师形成因材施教依据。
3. 学校形成课程改进证据。
4. 比赛材料形成可复核创新闭环。

## 6. 产品核心闭环

### 6.1 一条主闭环

采集证据 -> 诊断画像 -> 生成路径 -> 伴学干预 -> 学生行动 -> 验证掌握 -> 反思沉淀 -> 更新画像

### 6.2 学生视角

1. 进入“今日学习路径”。
2. 系统显示当前项目阶段和能力短板。
3. 学生选择当前卡点或提交学习证据。
4. 学伴给出下一步行动。
5. 学生完成微任务。
6. 系统检查证据。
7. 学生写反思。
8. 系统更新长期记忆。

### 6.3 教师视角

1. 创建课程能力图谱和项目任务。
2. 设置 Rubric 与 AI 边界。
3. 查看班级风险队列。
4. 复核高风险建议。
5. 观察学生成长趋势。
6. 调整课程节奏。

### 6.4 系统视角

1. 读取多源证据。
2. 映射到能力图谱。
3. 判断知识状态与项目状态。
4. 排序候选行动。
5. 生成脚手架提示。
6. 写入证据与记忆。

## 7. 第一版产品形态

第一版不做大而全后台，而做一个完整、可用、可演示、可继续扩展的核心产品。

### 7.1 学生端：今日学习路径

核心页面：

1. 当前项目阶段
2. 当前能力状态
3. 今日推荐任务
4. 学伴对话
5. 任务完成证据
6. 反思卡片

学生看到的不是大量数据，而是：

今天做什么。  
为什么做。  
做到什么程度算完成。  
遇到困难怎么获得提示。  
做完之后如何沉淀。

### 7.2 学伴对话：受控智能辅导

功能：

1. 学生描述问题。
2. 系统识别问题类型。
3. 系统决定提示层级。
4. 如果请求直接答案，系统拒绝替写并改为脚手架。
5. 必要时升级给老师。

对话不是独立聊天框，而是绑定当前学习路径。

### 7.3 教师端：班级 GrowthOps

核心页面：

1. 班级能力热力图
2. 学生风险队列
3. 待复核 AI 建议
4. 课程节奏建议
5. 典型卡点归因

教师不是看“谁分低”，而是看：

谁现在需要什么帮助。  
哪一类能力全班普遍薄弱。  
哪些 AI 建议需要我确认。  
哪些教学内容需要回补。

### 7.4 课程端：能力图谱编辑器

教师配置：

1. 课程能力节点
2. 项目里程碑
3. Rubric
4. 允许的 AI 帮助范围
5. 禁止输出规则
6. 证据采集方式

### 7.5 增值评价中心：产品的价值证明层

第一版产品必须单独设计“增值评价中心”，但它不是面向学生排名的大屏，而是服务三类判断：

学生端：

1. 我相对于自己的起点在哪些能力上进步了。
2. 哪些进步有证据支持。
3. 哪些能力还只是“完成了任务”，不能算真正掌握。
4. 下一步做什么最可能带来新的成长证据。

教师端：

1. 哪些学生正在停滞。
2. 哪些学生表面活跃但能力增值不足。
3. 哪些 AI 干预带来了可观察变化。
4. 哪些结论不确定，需要教师补充评价。

评委/学校端：

1. 当前 Demo 能证明“增值计算逻辑可运行”。
2. 当前合成样本不能证明“真实课程已经显著提分”。
3. 后续试点如何采集基线、第 4 周、第 8 周数据。
4. 哪些指标可用于真实效果验证。

增值评价中心必须显式区分：

| 类型 | 回答的问题 | 允许用途 | 禁止用途 |
|---|---|---|---|
| 学生成长增值 VA | 学生是否相对自身起点成长 | 形成性反馈、路径调整、教师会谈 | 排名、贴标签、高利害评价 |
| 服务效益 SE | 系统/课程服务是否对群体有帮助 | 试点复盘、产品优化、学校报告 | 未经对照就宣称因果效果 |
| 过程活跃度 | 学生是否参与了任务 | 解释机制、提醒跟进 | 代替能力增值 |
| 证据覆盖度 | 判断是否有足够材料支持结论 | 可信度提示、补证建议 | 当作成长结果 |

## 8. MVP 功能范围

第一阶段只做一个能跑通的最小可用产品。

### 8.1 必须完成

1. 学生画像初始化
2. 能力图谱展示
3. 今日学习路径生成
4. 学伴对话与脚手架提示
5. 直接答案请求拦截
6. 学习证据上传或录入
7. 完成标准检查
8. 反思卡生成

## 11. 算法设计

### 11.1 学情诊断

输入：

1. 测验结果
2. 学习对话
3. 项目产物
4. 提交记录
5. 教师评价
6. 反思文本

输出：

1. 能力掌握度
2. 主要卡点
3. 证据可信度
4. 风险等级
5. 推荐干预类型

方法：

1. 规则诊断：适合第一版，透明可控。
2. 知识追踪：用于长期学习状态更新。
3. LLM 归因：用于提炼卡点和解释。
4. 教师反馈校准：用于修正模型偏差。

### 11.1.1 增值性教育评价算法

第一版采用透明、可解释、可演示的 MVP 算法，不一开始就上复杂黑箱模型。

核心变量：

1. `baseline_score`：学生进入任务前的能力基线。
2. `current_score`：学生当前阶段能力表现。
3. `expected_score`：基于起点、阶段和任务难度估计的应有水平。
4. `value_added`：当前表现相对预期水平的偏离。
5. `evidence_coverage`：支撑该判断的证据覆盖度。
6. `uncertainty_level`：不确定性等级。

MVP 计算方式：

```text
学习增值 VA = 当前能力准备度 - 应有能力准备度
```

其中：

```text
应有能力准备度 = 起点基线 + 阶段自然成长预期 + 任务难度修正
```

产品显示不直接说“你提高了 12 分”，而采用更适合教育场景的话术：

1. “你在边界测试维度已高于当前起点的预期轨迹。”
2. “该判断由 3 条证据支持：测试提交、解释文本、反思卡。”
3. “接口设计维度证据不足，暂不生成增值结论。”

禁止表达：

1. “系统已经证明你真实提分。”
2. “你的增值排名超过全班第几名。”
3. “AI 干预导致你成长。”
4. “你的能力已经被精准评定。”

允许表达：

1. “当前证据显示你相对起点有可观察进步。”
2. “这个维度仍需补充证据。”
3. “该判断用于学习反馈，不用于排名。”
4. “真实效果需要课程试点进一步验证。”

## 12. 可用产品的真实流程

### 12.0 增值评价贯穿原则

每条学习闭环都必须同时保存四类信息：

1. 起点：学生在任务前处于什么状态。
2. 行动：系统给了什么路径或脚手架。
3. 证据：学生完成了什么可观察行为。
4. 增值：相对预期轨迹是否出现可解释变化。

但系统必须避免一个常见错误：

> 学生成长了，不等于系统造成了成长。

因此产品内采用两层声明：

1. 学生成长 VA：用于学生反馈和教师诊断。
2. 服务效益 SE：只有在试点有对照、基线、随访和预注册指标后，才用于群体效果评估。

第一版 Demo 只展示 VA 计算链路，不夸大 SE。

### 流程 A：学生完成今日任务

1. 学生打开系统。
2. 系统显示今日学习路径。
3. 学生选择“开始任务”。
4. 系统给出任务背景、完成标准和禁止替写边界。
5. 学生提交过程证据。
6. 系统判断证据是否足够。
7. 不足则给脚手架提示。
8. 足够则进入反思。
9. 反思写入长期记忆。
10. 系统更新分维度学习增值，但保留证据和不确定性说明。

### 流程 B：学生卡住

1. 学生点击“我卡住了”。
2. 系统要求学生提供当前尝试、错误现象和目标。
3. 诊断智能体识别卡点。
4. 边界智能体判断是否有替写风险。
5. 伴学智能体给脚手架提示。
6. 学生完成下一步。
7. 系统记录哪类提示有效。

### 流程 C：教师复核

1. 系统发现高风险建议。
2. 教师收到待复核卡片。
3. 教师看到证据、AI 建议和边界说明。
4. 教师选择发布、修改或拒绝。
5. 结果写回学生路径和模型记忆。
