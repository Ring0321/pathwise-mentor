## 0. 本版更新说明

早期方案已经完成了选题定义、理论框架、开源资料参考、PlantUML 图集和长篇参赛文档。本版不再继续扩写抽象概念，而是把已经完成的可运行 Demo 固化为参赛方案的核心证据。

本版新增重点有四个：

1. 将产品主形态明确为“芋道教师工作台”，而不是零散演示页。
2. 将“增值性教育评价”落到软件工程课程 Rubric、能力图谱、证据账本和教师复核上。
3. 将闭环从“看起来能演示”提升为“自动化测试可验证”：教师决策、学生回流、阶段变化、JSON 导出和边界声明均已被本地浏览器流程测试覆盖。
4. 将 AI 能力边界写入产品设计：AI 只提供候选建议和脚手架，不自动评价学生、不自动发布、不替学生完成答案。

因此，本版方案的核心判断是：

> SE-Path 不是一个会聊天的编程助教，而是一个把软件工程学习证据转化为增值诊断、路径行动和教师复核的课程 GrowthOps 工作台。

## 1. 赛题理解与产品定位

### 1.1 赛题要求拆解

本赛题要求设计并实现面向特定学科专业的“自适应学习伙伴智能体”。从评分标准看，重点不是单一问答能力，而是能否形成完整教育闭环：

| 赛题要求 | SE-Path v2 对应实现 | 评委可观察证据 |
|---|---|---|
| 学情诊断 | 增值诊断单读取 Git、CI、PR、对话、反思和教师复核证据 | 页面展示学生当前能力、期望水平、差值、不确定性和证据覆盖 |
| 路径规划 | 六步学习改进闭环：学情诊断、安全门禁、实时干预、验证修复、教师复核、闭环完成 | 阶段进度条和状态随教师决策、学生回流实时变化 |
| 实时干预 | Safe-VOI 推荐只输出检查清单、最小失败用例、说明卡、迁移任务等脚手架 | 教师决策面板中明确“不含答案实现” |
| 记忆与反思 | 学生收到脚手架、补证据、提交反思后写入证据账本 | JSON 证据账本导出包含学生回流状态和记录 |
| Agent 能力 | 诊断、建议、复核、证据整理与导出形成可运行工作流 | `npm run test:flow` 覆盖真实浏览器点击流程 |
| 商业价值 | 基于芋道后台体系，面向高校软件工程课程可部署 | 采用 Vue3/Element Plus/管理台信息架构 |

### 1.2 产品一句话

SE-Path 学伴是一款面向软件工程项目制课程的自适应学习伙伴智能体，通过工程证据账本、增值性教育评价和 Safe-VOI 干预策略，把学生一次项目阻塞转化为可诊断、可干预、可复核、可沉淀的学习改进闭环。

### 1.3 与普通 AI 编程助手的区别

普通 AI 编程助手通常把学生问题当成一次输入输出：学生问，模型答，答案结束。SE-Path 的产品逻辑完全不同：

1. 它首先读取学习证据，而不是直接回答。
2. 它先判断证据是否足够，而不是强行给结论。
3. 它把 AI 输出限定为候选建议和脚手架，而不是交付答案。
4. 它把教师作为发布门和复核者，而不是绕过教师。
5. 它把每次干预后的学生回流写入账本，用于后续增值评价。

因此，SE-Path 的竞争优势不在“模型回答更像人”，而在“教育过程更可控、更可解释、更能持续改进”。

## 2. 目标用户与首版场景

### 2.1 首版用户

首版只做一个明确场景：高校软件工程项目制课程中的教师工作台。

目标教师用户包括：

1. 软件工程、Web 后端、项目实训、数据库应用等课程教师。
2. 需要批量跟踪学生项目过程的助教。
3. 需要复核 AI 建议是否可发布的课程负责人。

目标学生用户包括：

1. 正在完成项目制作业的计算机相关专业学生。
2. 在需求、接口、测试、事务、协作、发布等能力维度上存在不同薄弱点的学生。
3. 容易依赖 AI 直接给答案、但需要被引导形成工程思维的学生。

### 2.2 首版课程场景

当前 Demo 选用“REST API 错误处理与边界测试”作为首个可演示课程任务，理由如下：

1. 它天然具有软件工程证据：PR、CI、测试覆盖、错误日志、接口契约、学生对话。
2. 它不是纯知识点问答，而是要求学生把需求和异常路径转化为可执行测试。
3. 它适合体现 Safe-VOI：系统应给检查清单和最小失败用例模板，而不是直接写修复代码。
4. 它适合体现教师复核：证据不足时不应自动评价学生，只能退回补证据。

### 2.3 当前样例学生

当前工作台默认样例为学生“林知行”：

| 字段 | 内容 |
|---|---|
| 班级 | 软件工程 2301 |
| 课程任务 | REST API 错误处理与边界测试 |
| 触发事件 | PR #18 CI 失败 |
| 风险等级 | high |
| 当前阶段 | 学情诊断 |
| 证据覆盖 | 34% |
| 增值焦点 | 边界测试设计 |
| 当前水平 | 50 |
| 期望水平 | 54 |
| 差值 | -4 |
| 不确定性 | high |

这个样例故意不是“已经成功”的学生，而是一个高风险、低证据覆盖、需要教师决策的真实教学场景。这样可以充分展示系统如何处理不确定性，而不是只展示漂亮结果。

## 3. 产品总架构

### 3.1 三层产品结构

SE-Path v2 按三层设计：

| 层级 | 名称 | 职责 |
|---|---|---|
| 课程配置层 | Rubric 与能力图谱 | 定义课程能力维度、权重、证据来源、安全门禁和不确定性规则 |
| 运行工作台层 | 芋道教师工作台 | 呈现班级工单、增值诊断单、Safe-VOI 建议、教师决策和学生回流 |
| 证据与验收层 | 证据账本与自动化 QA | 记录每次诊断、决策、回流、导出和边界声明，形成可审计证据 |

三层之间不是页面堆叠，而是数据闭环：

1. Rubric 定义什么能力值得评价。
2. 工程证据进入诊断单。
3. Safe-VOI 根据证据缺口给候选行动。
4. 教师确认行动是否发布。
5. 学生收到脚手架、补证据、写反思。
6. 新证据回到证据账本。
7. 增值评价重新计算当前水平、覆盖率和阶段。

### 3.2 信息架构

当前教师工作台包括七个一级功能入口：

| 导航项 | 当前作用 | 后续上线扩展 |
|---|---|---|
| 工作台 | 课程整体概况与待办入口 | 课程周报、风险趋势、教学行动建议 |
| 学情看板 | 班级学习状态概览 | 多班级、多课程对比，但不做学生排名 |
| 学生档案 | 单个学生的长期证据与反思 | 学生确认/纠错机制、长期记忆版本 |
| 增值诊断 | 当前主闭环页面 | 从单个诊断单扩展到批量处理 |
| 任务与反馈 | 学生端脚手架与补证据任务 | 接入 LMS/飞书/企业微信通知 |
| Rubric 配置 | 课程能力图谱、权重、证据源、安全规则 | 版本化 Rubric、教师标注校准 |
| 设置 | 课程边界、隐私与账号配置 | 芋道 RBAC、多租户、数据权限 |

当前实现重点放在“增值诊断”和“Rubric 配置”，因为这两项最能体现本项目与普通 AI 答疑工具的差异。

### 3.3 技术形态

当前正式 Demo 工程为：

`sepath-yudao-teacher-console`

技术栈为：

| 技术 | 用途 |

| Element Plus | 生产级后台组件 |

## 4. 核心对象模型

### 4.1 LearningWorkOrder

`LearningWorkOrder` 是教师工作台的核心对象，代表一次可处理的学习工单。它不是普通待办，而是学习证据、增值诊断和路径状态的聚合。

关键字段包括：

| 字段 | 含义 |
|---|---|
| id | 工单唯一编号 |
| studentName / studentNo | 学生身份信息 |
| courseClass / courseName | 所属班级与课程任务 |
| trigger | 触发事件，如 PR 失败、CI 异常、协作争议 |
| risk | 风险等级 |
| status | 当前状态：diagnosis、evidence、guardrail、review |
| evidenceCoverage | 证据覆盖率 |
| diagnosis | 当前学情诊断文字 |
| valueAdded | 增值评价维度 |
| collectedEvidence | 已采集证据 |
| missingEvidence | 待补证据 |
| safeVoiRecommendation | Safe-VOI 推荐行动 |
| safeVoiReason | 推荐理由 |
| stages | 六步闭环阶段 |

### 4.2 EvidenceEvent

`EvidenceEvent` 是最小证据单元。当前证据来源包括：

1. GitHub Actions 的 CI 失败日志。
2. Pull Request 变更摘要。
3. 学伴对话中的学生求助记录。
4. 测试策略检查表。
5. 故障最小化原则下的最小失败用例。
6. 教师复核记录。
7. 学生反思卡。

系统强调“证据先行”：没有证据的结论不能进入学生画像，只能以“不确定/待补证据”的方式展示。

### 4.3 ValueAddedDimension

`ValueAddedDimension` 表达单个能力维度上的形成性增值判断：

| 字段 | 含义 |
|---|---|
| label | 能力维度名称 |
| current | 当前观测水平 |
| expected | 基于起点和阶段的期望水平 |
| delta | 当前水平与期望水平差值 |
| uncertainty | 不确定性等级 |
| description | 能力定义 |

当前样例中，“边界测试设计”的 current 为 50，expected 为 54，delta 为 -4。由于证据覆盖只有 34%，系统不会把这个差值解释为确定性能力不足，而是标注高不确定性并建议补证据。

### 4.4 TeacherDecision

教师决策有三类：

| 决策 | 含义 | 设计边界 |
|---|---|---|
| approve | 批准脚手架 | 只发布检查清单、测试骨架或任务拆解，不含答案实现 |
| returnEvidence | 退回补证据 | 证据不足时要求学生补充检查清单、最小失败用例或设计说明 |
| humanTalk | 转人工会谈 | 涉及协作冲突、责任归因、高语境判断时转教师会谈 |

AI 可以推荐，但不能替教师选择。教师点击后才会写入证据账本。

### 4.5 EvidenceLedgerEntry

`EvidenceLedgerEntry` 是所有关键动作的审计记录。当前账本记录类型包括：

1. baseline：基线或初始诊断。
2. evidence：已采集证据。
3. gap：证据缺口。
4. recommendation：Safe-VOI 推荐。
5. decision：教师确认。
6. student_return：学生回流。

每条记录包含 actor、source、detail、traceId、stageAfter、evidenceCoverageAfter 等字段，用于后续导出、复盘和答辩说明。

## 5. 学习闭环设计

### 5.1 六步闭环

当前产品闭环为六步：

| 步骤 | 名称 | 触发条件 | 产出 |
|---|---|---|---|
| 1 | 学情诊断 | 读取 PR/CI/对话/反思等证据 | 诊断单、能力差值、不确定性 |
| 2 | 安全门禁 | 判断是否能给干预建议 | 是否允许发布脚手架 |
| 3 | 实时干预 | 教师确认后发出脚手架 | 检查清单、最小失败用例、说明卡 |
| 4 | 验证修复 | 学生提交新证据 | 新 CI、测试、PR、设计说明 |
| 5 | 教师复核 | 教师确认是否可放行 | 教师决策与复核记录 |
| 6 | 闭环完成 | 学生提交反思并形成新证据 | 反思卡、下一次迁移承诺、增值更新 |

这六步直接对应赛题的诊断、规划、干预、记忆与反思要求。

### 5.2 当前可运行闭环

当前 Demo 的一条完整路径如下：

1. 学生林知行的 PR #18 触发 CI 失败。
2. 系统读取 CI 失败日志、PR 变更摘要和学生求助记录。
3. 系统发现“边界测试设计”维度证据覆盖不足，当前证据覆盖 34%。
4. Safe-VOI 推荐“先补异常路径检查清单和最小失败用例，不给完整代码”。
5. 教师选择“退回补证据”。
6. 系统写入教师决策账本，阶段进入“补证据”，证据覆盖保持 34%，不人为抬高。
7. 学生端依次确认收到任务、提交补充证据、提交反思卡。
8. 系统写入三条 student_return 账本记录。
9. 阶段进入“闭环完成”。
10. 证据覆盖提升至 58%。
11. 教师可导出 JSON 证据账本。

这条路径已经由本地浏览器自动化测试覆盖，不只是静态页面。

### 5.3 为什么选择“退回补证据”作为默认演示

很多参赛作品会默认展示 AI 给出漂亮建议。SE-Path 反而选择“证据不足，不直接判断”的场景，原因是：

1. 这更接近真实教学。
2. 能体现增值评价的严谨性。
3. 能体现 AI 边界。
4. 能体现教师复核价值。
5. 能避免把一次 CI 失败夸大为学生能力缺陷。

对评委来说，这个设计比“AI 直接给出修复方案”更有教育可信度。

## 6. 增值性教育评价设计

### 6.1 增值评价不是排名

本项目中的“增值”不是学生排名，也不是惩罚依据，更不是就业预测。它只回答一个形成性问题：

> 在给定起点、任务阶段和证据条件下，学生相对于自己应有轨迹是否出现了可观察变化；下一步怎样获得更可靠的学习证据。

因此，系统所有页面和导出账本都必须保留边界声明：

1. 形成性诊断，不排名不惩罚。
2. AI 只提供候选建议，教师确认后生效。
3. 证据不足时标注不确定性。
4. 不把过程活跃度直接当作能力提升。
5. 不把原型指标包装成真实课程成效。

### 6.2 当前增值计算展示

当前诊断单展示四个关键指标：

| 指标 | 当前样例 |
|---|---|
| 当前水平 | 50 |
| 期望水平 | 54 |
| 差值 | -4 |
| 不确定性 | 高 |

由于证据覆盖低，系统给出的不是“学生差”，而是：

> 基于当前证据，可能低估了真实水平；补充缺失证据可显著降低不确定性。

这个表达避免了教育系统常见的过度判断问题。

### 6.3 证据覆盖与不确定性

证据覆盖是系统是否能下结论的前置条件。当前规则设计如下：

| 证据覆盖 | 系统行为 |
|---|---|
| 低于 60% | 只能退回补证据或发布检查清单 |
| 60%-70% | 可以给低风险脚手架，但需标注不确定性 |
| 高于 70% | 可进入迁移任务或教师复核 |
| 涉及协作、责任、发布风险 | 必须教师确认 |

这使系统在教育场景中更稳健：宁可慢一步补证据，也不做无证据自动判断。

### 6.4 VA 与 SE 分离

本项目区分两种指标：

| 指标 | 含义 | 是否可直接归因 |
|---|---|---|
| VA 学生成长增值 | 学生相对于自身起点的可观察变化 | 不直接归因给系统 |
| SE 服务效能 | 系统是否提高证据完整度、教师处理效率和闭环完成率 | 可作为平台运营指标 |

这种分离可以避免宣传过度。比赛材料中可以说“原型验证了闭环和证据机制”，但不能说“已经证明显著提高成绩”。

## 7. Safe-VOI 干预策略

### 7.1 设计原则

Safe-VOI 表示“安全约束下的信息价值”。它不是简单推荐下一题，而是判断哪种行动最能降低不确定性、最能产生新学习证据，同时不会替代学生完成任务。

当前策略原则：

1. 高证据缺口优先补证据。
2. 高风险任务优先教师复核。
3. 低风险且证据充分时才允许发布脚手架。
4. 任何情况下不输出可直接提交的完整代码。
5. 学生请求直接答案时，转为检查清单、问题分解或教师复核。

### 7.2 当前 Safe-VOI 推荐

林知行样例中的推荐为：

> 先补异常路径检查清单和最小失败用例，不给完整代码。

推荐理由为：

> 可最大幅度降低不确定性，且不替代学生完成实现。

这个设计对评委的价值在于：系统既智能，又克制；既能行动，又不越界。

### 7.3 三类教师决策

教师面板中给出三类操作：

1. 批准脚手架：生成最小化脚手架与测试骨架，不含答案实现。
2. 退回补证据：请学生补充缺失证据后重新诊断。
3. 转人工会谈：安排一对一会谈，处理高语境问题。

每个操作都写入账本，形成“AI 建议 -> 教师确认 -> 学生行动 -> 证据回流”的闭环。

## 8. Rubric 与能力图谱配置

### 8.1 为什么要有 Rubric 配置页

如果系统只有一个固定样例，评委会质疑它只是写死的 Demo。Rubric 配置页解决这个问题：

1. 教师可以配置课程能力维度。
2. 每个维度有权重、目标增值、证据覆盖、安全动作和不确定性规则。
3. 能力图谱把需求、接口、异常、事务、协作、发布串成学习路径。
4. 诊断单从配置读取课程标准，而不是依赖静态文案。

### 8.2 当前 Rubric 维度

| 维度 | 类别 | 权重 | 目标增值 | 证据覆盖 | 安全动作 |
|---|---|---:|---:|---:|---|
| 边界测试设计 | 测试与质量 | 22 | +4 | 68% | 异常路径检查清单 + 最小失败用例模板 |
| 事务边界建模 | 后端设计 | 20 | +4 | 56% | 事务路径说明卡 + 回滚场景提示 |
| 需求澄清与接口契约 | 需求与协作 | 18 | +3 | 76% | 接口契约迁移任务 |
| 协作评审表达 | 团队工程 | 18 | +3 | 61% | 评审表达反思卡 + 教师会谈 |
| 发布前验证 | 交付质量 | 22 | +5 | 64% | 上线验收卡 + 回滚计划模板 |

当前权重合计 100%，说明课程评价规则完整。证据就绪度为 65%，说明部分维度仍需要补证据。

### 8.3 能力图谱

当前能力图谱为六级：

| 层级 | 能力节点 | 关系 |
|---|---|---|
| L1 | 需求澄清 | 先把需求边界说清楚 |
| L2 | 接口契约 | 再形成可验收的接口约束 |
| L3 | 异常与边界 | 把约束转成失败路径和测试用例 |
| L4 | 事务一致性 | 覆盖回滚、重试和并发冲突 |
| L5 | 协作评审 | 把修复策略清楚交付给同伴和教师 |
| L6 | 发布验证 | 形成上线前的可复核证据链 |

这条路径让软件工程学习从“知识点列表”变成“项目交付能力链”。

### 8.4 证据源映射

| 证据源 | 类型 | 说明 | 适用维度 |
|---|---|---|---|
| Git | 代码过程 | 提交节奏、变更范围、回滚记录和协作痕迹 | 事务边界、协作评审、发布前验证 |
| CI | 自动验证 | 失败日志、测试覆盖、回归结果和质量门禁 | 边界测试、事务边界、发布验证 |
| 学伴对话 | 解释证据 | 学生提问、困难自述、概念解释和学习请求 | 需求澄清、边界测试 |
| 反思卡 | 回流证据 | 修复策略、迁移计划、风险自评和下一次承诺 | 协作评审、边界测试、发布验证 |
| 教师复核 | 人工确认 | 高语境判断、发布确认、会谈结论和评价边界 | 协作评审、发布验证 |

## 9. 证据账本与导出

### 9.1 账本的产品价值

证据账本是 SE-Path 区别于普通智能助手的关键。它解决三个问题：

1. 诊断从哪里来。
2. 教师做了什么确认。
3. 学生后续是否真的产生了学习证据。

没有证据账本，AI 建议就是黑箱。加入账本后，系统变成可审计、可复核、可参赛说明的教育产品。

| studentReturn | 学生回流状态 |
| studentReturnProgress | 学生回流进度 |
| currentStage | 当前阶段 |
| evidenceCoverage | 证据覆盖 |
| valueAdded | 增值评价 |

## 10. 芋道落地设计

### 10.1 为什么选择芋道

本项目选择芋道管理台风格作为前端落地参考，原因是：

1. 芋道适合做真实后台，而不是营销展示页。
2. Element Plus 组件体系适合表格、表单、抽屉、标签、进度、步骤条等教学运营工作台。
3. 芋道体系天然包含 RBAC、多租户、数据权限、组织管理等后台能力，适合未来高校/机构部署。
4. 赛题评委会更看重“能上线”，芋道形态比临时 Demo 页面更可信。

### 10.2 页面与组件映射

| 产品功能 | 当前组件形态 | 后续芋道落地 |
|---|---|---|
| 班级工单队列 | 卡片/筛选/风险标签 | `ElTable` + 查询表单 + 分页 |
| 增值诊断单 | 诊断卡、证据列、决策面板 | 详情页 + 右侧复核栏 |
| 证据账本 | `ElDrawer` + `ElTimeline` | 审计日志表 + 导出权限 |
| 学生回流 | 三步按钮 + 进度 | 学生端任务表 + 回流 API |
| Rubric 配置 | 表格/卡片双端适配 | 配置表单 + 版本管理 |
| 能力图谱 | 能力节点卡片 | 图谱组件 + Rubric 绑定 |

### 10.3 当前视觉原则

当前页面放弃过度“AI 感”的大渐变、炫光、卡片堆叠，改用更像真实后台的设计：

1. 左侧课程导航。
2. 顶部班级/课程/教师上下文。
3. 中心诊断单作为主任务。
4. 右侧教师复核和 Safe-VOI 建议。
5. 底部证据与闭环进度。
6. 移动端压缩为单列可读结构。

这符合“教师每天会用”的产品逻辑，而不是一次性演示海报。

### 12.1 三分钟演示路径

2. 展示已采集证据：CI 失败日志、PR 变更摘要、学生求助记录。

4. 说明系统认为证据覆盖只有 34%，所以不直接判断能力不足。
5. 展示 Safe-VOI 推荐：先补检查清单和最小失败用例，不给完整代码。

第三分钟：展示教师决策、学生回流和导出

## 14. 页面级产品规格

### 14.1 教师工作台首页

教师工作台首页不是营销页，而是课程当天的操作入口。它应回答教师每天最关心的四个问题：

1. 今天哪些学生需要处理。
2. 哪些工单风险最高。
3. 哪些证据不足，不能贸然判断。
4. 哪些 AI 建议已经可以由教师确认发布。

首页的核心模块包括：

| 模块 | 当前 v2 能力 | 后续上线规格 |
|---|---|---|
| 课程上下文 | 显示软件工程 2301 与当前课程任务 | 支持课程切换、班级切换和教师角色切换 |
| 工单队列 | 多学生工单、风险/状态筛选 | 支持分页、批量标记、负责人分配 |
| 状态摘要 | 风险、证据覆盖、当前阶段 | 增加本周趋势、未处理时长、重复风险 |
| 快捷入口 | 进入增值诊断单、Rubric 配置 | 接入课程配置、通知中心、验收看板 |

首页的设计原则是“少而准”。评委三分钟内必须能看懂当前系统不是 AI 聊天页面，而是课程运营工作台。

### 14.2 增值诊断单

增值诊断单是产品主界面。它的目标不是展示所有数据，而是把一次学习阻塞整理成教师可决策的信息结构。

页面从上到下分为六块：

1. 学生和触发事件：展示学生姓名、学号、触发事件、发生时间、风险、证据覆盖和诊断边界。
2. 增值焦点：展示当前能力维度、当前水平、期望水平、差值和不确定性。
3. 证据区：区分已采集证据与待补证据，避免把缺证据场景伪装成确定结论。
4. Safe-VOI 建议：说明系统认为下一步最有价值、最安全的行动是什么。
5. 教师决策：教师选择批准脚手架、退回补证据或转人工会谈。
6. 学习闭环：展示六阶段进度和学生回流状态。

该页面的关键体验是“教师一眼能判断是否可以行动”。如果证据不足，页面应把“待补证据”放在显眼位置；如果需要人工复核，页面应把 AI 输出降级为证据摘要。

### 14.3 证据账本抽屉

证据账本采用抽屉而不是单独页面，原因是教师处理工单时不能丢失上下文。抽屉打开后应保留当前学生和诊断状态，同时展示完整时间线。

账本应包含：

1. 基线和初始诊断。
2. 已采集证据。
3. 证据缺口。
4. Safe-VOI 推荐。
5. 教师决策。
6. 学生回流。
7. 阶段变化。
8. 证据覆盖变化。
9. traceId。
10. 导出入口。

账本不是为了好看，而是为了回答评委和教师的同一个问题：这个结论从哪里来，谁确认过，学生后来做了什么。

### 14.4 Rubric 配置页

Rubric 配置页承担课程初始化职责。没有它，系统容易被看作固定 Demo；有了它，系统才像可复用产品。

配置页应支持：

1. 启用或停用能力维度。
2. 调整能力权重。
3. 查看证据覆盖。
4. 查看安全动作。
5. 查看能力图谱节点。
6. 查看证据源映射。
7. 保存、恢复默认、导出配置。
8. 在手机端使用卡片而不是横向表格。

当前 v2 已实现这些核心能力的本地版本。

### 14.5 学生回流区

学生回流区是闭环能否成立的关键。很多 AI 教育产品只展示“系统给建议”，但没有证明学生是否真的行动。SE-Path 把学生回流拆成三个节点：

| 节点 | 说明 | 写账本条件 |
|---|---|---|
| 确认收到任务 | 学生端收到脚手架或补证据卡 | 必须已有教师决策 |
| 提交补充证据 | 学生回传检查清单、最小失败用例或设计说明 | 必须已有教师决策 |
| 提交反思卡 | 学生写入修复策略与迁移承诺 | 必须已有教师决策 |

自动化测试已经验证：没有教师确认前，学生回流按钮禁用；教师确认后，三步回流才能写入账本。

## 15. 角色权限与治理

### 15.1 角色模型

后续接入芋道 RBAC 时，至少需要四类角色：

| 角色 | 可见范围 | 可操作事项 | 禁止事项 |
|---|---|---|---|
| 学生 | 自己的任务、反馈、证据和反思 | 提交补证据、提交反思、确认任务 | 查看他人数据、修改 Rubric |
| 教师 | 所负责课程和班级 | 查看工单、确认建议、导出账本、配置 Rubric | 自动批量评价学生 |
| 课程负责人 | 多班级课程 | 管理 Rubric 版本、查看课程级指标 | 查看无授权原始隐私数据 |
| 管理员 | 租户与系统配置 | 账号、权限、数据保留策略 | 参与教学结论判断 |

角色设计的底线是：系统管理员不应替代教师做教育判断，AI 也不应绕过教师发布高风险结论。

### 15.2 数据权限

数据权限应按课程、班级、学生和证据类型分层：

1. 学生只能看自己的记录。
2. 任课教师只能看自己课程或班级内的学生。
3. 课程负责人可看聚合指标，但默认不看原始对话细节。
4. 导出数据必须脱敏或记录授权。
5. 涉及学生反思和对话的内容应有更高敏感级别。

### 15.3 审计规则

任何会影响学生路径的动作都必须写审计：

| 动作 | 是否审计 | 理由 |
|---|---|---|
| 教师批准脚手架 | 是 | 会触发学生任务 |
| 教师退回补证据 | 是 | 会改变学习路径 |
| 教师转人工会谈 | 是 | 涉及人工介入 |
| 学生提交证据 | 是 | 会改变证据覆盖 |
| Rubric 权重修改 | 是 | 会影响诊断规则 |
| AI 生成候选建议 | 是 | 需要追踪模型输出和上下文 |

审计不是为了追责学生，而是为了保证教育系统的透明性和可复核性。

## 16. 状态机与业务规则

### 16.1 工单状态

当前 `WorkOrderStatus` 包括四类：

| 状态 | 含义 | 页面表现 |
|---|---|---|
| diagnosis | 处于学情诊断 | 需要教师先阅读证据 |
| evidence | 处于补证据 | 需要学生或教师补充证据 |
| guardrail | 处于安全门禁 | 等待教师确认是否可发布脚手架 |
| review | 处于教师复核 | 等待教师处理高语境判断 |

### 16.2 阶段推进规则

当前阶段由教师决策和学生回流共同决定：

| 条件 | 阶段 |
|---|---|
| 无教师决策 | 读取工单初始阶段 |
| 教师批准脚手架 | 安全门禁 |
| 教师退回补证据 | 补证据 |
| 教师转人工会谈 | 人工会谈 |
| 学生确认收到任务 | 实时干预或补证据回流 |
| 学生提交补充证据 | 验证修复 |
| 学生提交反思卡 | 闭环完成 |

这种设计避免“按钮只是改变颜色”的演示感。每一次操作都会改变业务状态，并写入可导出的证据账本。

### 16.3 证据覆盖更新规则

证据覆盖不是简单加分，而是随证据质量变化：

1. 教师退回补证据时，证据覆盖不变，因为还没有新证据。
2. 学生确认收到任务后，只说明任务触达，覆盖小幅提升。
3. 学生提交补充证据后，覆盖显著提升。
4. 学生提交反思卡后，覆盖进一步提升。
5. 最终覆盖仍不是满分，避免把一次回流包装成完整能力证明。

当前自动化验证路径中，证据覆盖从 34% 提升到 58%，体现的是“证据更完整”，不是“学生能力立刻满分”。

### 16.4 边界拦截规则

系统必须拦截以下情况：

| 情况 | 处理 |
|---|---|
| 学生要求直接答案 | 转为脚手架、追问、检查清单或教师复核 |
| 证据覆盖不足 | 标注不确定性，退回补证据 |
| 协作争议 | AI 只整理证据，转教师复核 |
| 发布风险 | 教师确认前不得放行 |
| Rubric 未配置 | 不生成确定性诊断 |

## 18. 验收用例

### 18.1 用例 1：证据不足时不得直接下结论

前置条件：

1. 学生林知行证据覆盖为 34%。
2. 待补证据包括异常路径检查清单和最小失败用例。

操作：

1. 打开增值诊断单。
2. 查看 Safe-VOI 推荐。

期望结果：

1. 页面显示高不确定性。
2. 推荐为补证据或检查清单。
3. 不展示完整代码答案。
4. 不把学生标记为确定性能力不足。

### 18.2 用例 2：教师决策写账本

操作：

1. 点击“退回补证据”。

期望结果：

1. `selectedDecision` 变为 `returnEvidence`。
2. 账本新增 `decision` 类型记录。
3. 阶段变为“补证据”。
4. 证据覆盖保持 34%。
5. JSON 导出中包含教师确认记录。

### 18.3 用例 3：学生回流受教师确认约束

前置条件：

1. 页面重置，无教师决策。

期望结果：

1. 学生回流按钮全部禁用。
2. 点击不会写入账本。

教师确认后：

1. 三个学生回流按钮可按顺序写入。
2. 账本新增三条 `student_return`。
3. 阶段变为“闭环完成”。
4. 证据覆盖提升到 58%。

### 18.4 用例 4：Rubric 不是静态展示

操作：

1. 打开 `?view=rubric`。
2. 修改某个维度权重。
3. 保存配置。
4. 恢复默认。
5. 导出配置。

期望结果：

1. 权重合计实时变化。
2. 保存后本地可持久化。
3. 恢复默认后回到初始 Rubric。
4. 导出 JSON 包含 Rubric、能力图谱、证据源和边界说明。

## 19. 后端迁移路线

### 19.1 当前本地状态

当前 v2 为本地可运行原型，状态来源包括：

1. `src/mock/workbench.ts`
2. `src/mock/rubric.ts`
3. `localStorage`
4. 浏览器端 JSON 导出

这种方式适合比赛初赛和本地演示，但不适合真实多用户部署。

### 19.2 迁移到后端后的数据表

建议后端最小表结构：

| 表 | 作用 |
|---|---|
| course | 课程与班级 |
| user | 学生、教师、管理员 |
| work_order | 学习工单 |
| evidence_event | 证据事件 |
| evidence_ledger | 证据账本 |
| teacher_decision | 教师决策 |
| student_return | 学生回流 |
| rubric_dimension | Rubric 维度 |
| ability_graph_node | 能力图谱节点 |
| safe_voi_recommendation | 候选干预建议 |
| audit_log | 审计日志 |

### 19.3 API 迁移顺序

建议按以下顺序迁移：

1. 先迁移 `work-orders` 列表与详情。
2. 再迁移教师决策写入。
3. 再迁移学生回流写入。
4. 再迁移账本导出。
5. 最后迁移 Rubric 配置和 Safe-VOI 推荐。

这样可以保证主闭环先上线，不被复杂配置拖慢。

### 19.4 与芋道后端的结合

接入芋道时建议：

1. 用芋道用户体系承载学生、教师、管理员。
2. 用租户隔离不同学校或机构。
3. 用数据权限隔离课程与班级。
4. 用字典管理风险等级、工单状态、证据状态。
5. 用操作日志记录教师决策和配置修改。
6. 用文件服务保存导出的证据账本。

## 20. 开源项目吸收与创新边界

### 20.1 可借鉴的开源能力

| 方向 | 代表项目/技术 | 可借鉴能力 | SE-Path 自研增量 |
|---|---|---|---|
| 后台管理 | 芋道、ruoyi-vue-pro、Element Plus | RBAC、多租户、表格表单、后台布局 | 教学证据账本、Rubric 安全门禁、增值诊断单 |
| Agent 编排 | LangGraph 等状态图框架 | 状态机、人工介入、流程编排 | 将 Agent 状态绑定教师复核和学生回流 |
| RAG/知识库 | LlamaIndex、RAGFlow | 课程资料检索、知识边界 | 输出必须被 Rubric 和 Safe-VOI 约束 |
| 自动评测 | PrairieLearn、Autograder、CI | 测试结果、作业评测 | 把评测结果转化为形成性证据 |
| LLM 测试 | DeepEval 等 | 模型输出回归测试 | 测试“不能给答案、必须标注不确定性” |

### 20.2 不能简单照搬的地方

1. 不能把自动评测分数直接当成学生能力。
2. 不能把 RAG 回答当作已验证教学结论。
3. 不能把 Agent 自动完成任务当作学习成效。
4. 不能把后台系统的权限管理当作教育治理的全部。
5. 不能把开源工具堆叠成“技术大杂烩”。

SE-Path 的创新在于把这些底座能力重新组织成教育闭环：

> 工程证据 -> Rubric 约束 -> 增值诊断 -> Safe-VOI 行动 -> 教师复核 -> 学生回流 -> 证据账本。

## 22. 风险与边界

### 14.1 产品风险

| 风险 | 应对 |
|---|---|
| 被误解为自动评分系统 | 页面和导出中明确“形成性诊断，不排名不惩罚” |
| 被误解为代码代写工具 | Safe-VOI 只给脚手架，不给答案实现 |
| 证据不足时误判学生 | 证据覆盖和不确定性作为前置门禁 |
| 教师负担增加 | 工单队列和证据摘要减少信息整理成本 |
| Demo 被质疑静态 | 用 `test:flow` 和 JSON 导出证明真实交互 |

### 14.2 伦理边界

系统不得：

1. 自动给学生排名。
2. 自动惩罚学生。
3. 自动预测就业或能力上限。
4. 自动发布高风险教学结论。
5. 把学生一次失败扩大成长期标签。
6. 把 AI 生成内容当成学生真实能力证据。

系统可以：

1. 汇总候选证据。
2. 标注不确定性。
3. 推荐低风险脚手架。
4. 提醒教师复核。
5. 记录学生反思和补证据。
6. 帮助教师做形成性支持。

## 25. 本版结论

SE-Path v2 已经完成从“概念方案”到“可运行产品闭环”的关键跃迁。

它现在能够证明：

1. 学习诊断不是凭空生成，而是来自工程证据。
2. 增值评价不是排名，而是形成性支持。
3. AI 干预不是替写答案，而是 Safe-VOI 脚手架。
4. 教师不是被替代，而是发布门和复核者。
5. 学生不是被静态标签化，而是通过补证据和反思进入新的学习闭环。
6. 页面不是静态展示，而是有工单切换、状态持久化、账本导出、Rubric 配置和自动化测试。

这正是本项目参加“自适应学习伙伴智能体”赛题时最应该强调的创新：

> 把大模型从“回答机器”变成“受证据约束、受教师复核、服务学生成长增值的学习路径行动系统”。
