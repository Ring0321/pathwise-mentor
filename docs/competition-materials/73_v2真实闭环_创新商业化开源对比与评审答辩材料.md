# 73 v2 真实闭环：创新点、商业化、开源对比与评审答辩材料

生成日期：2026-08-24  
适用版本：`sepath-yudao-teacher-console` v2 真实闭环版  
推荐用途：初赛补充材料、答辩追问、PPT 第 12 页后的备查材料  

---

## 1. 一句话定位

SE-Path 学伴不是聊天式 AI 助教，而是面向软件工程项目式学习的“证据驱动学习闭环工作台”：把 PR、CI、Review、学伴对话、教师复核和学生反思统一写成证据账本，再用 Safe-VOI 和增值评价选择下一步脚手架行动，最终由教师确认发布。

## 2. 一等奖创新主张

| 创新主张 | 普通方案怎么做 | SE-Path v2 怎么做 | 可核验证据 |
|---|---|---|---|
| 证据原生，而不是问答原生 | 学生提问，AI 回答 | 失败 PR/CI 先进入 EvidenceEvent，再形成诊断、待补证和干预建议 | `src/types.ts`、证据账本 JSON |
| 增值评价，而不是一次性评分 | 给分、排名或预测 | 对照起点、当前、期望、差值、不确定性，服务形成性支持 | 增值诊断单、`ValueAddedDimension` |
| Safe-VOI，而不是直接推荐 | 推荐下一题或下一段答案 | 按学习价值、风险、可逆性、证据覆盖、教师负担筛选下一步，只给脚手架 | Safe-VOI 推荐区、算法流程图 28 |
| 教师发布门，而不是 AI 自动决策 | AI 自动判断学生状态 | 教师选择批准脚手架、退回补证据、转人工会谈；AI 只做候选建议 | `TeacherDecision`、教师复核账本 |
| Rubric as Course Policy | 课程规则写在文档里 | Rubric、能力图谱、证据来源、低证据边界在工作台可配置 | `RubricWorkbench.vue` |
| 学生回流闭环 | 干预发出去后结束 | 学生接收任务、补证据、提交反思，系统更新阶段和覆盖率 | 学生回流截图、flow test |
| 可导出证据账本 | 只有页面展示 | 每次诊断、建议、教师确认、学生补证据都可导出 JSON | `SE-Path证据账本_林知行_wo-se-018.json` |
| 芋道化落地 | 原型页孤立存在 | Vue3 + Element Plus + 芋道管理台信息架构，后续可接 RBAC、多租户、数据权限 | v2 PPT、架构图 26 |

**答辩收束句：**我们的创新不是让模型回答得更像老师，而是让每个学习建议都能回到证据、边界、教师确认和学生增值。

## 3. 与开源生态的关系

本项目主动参考成熟开源生态，但不把开源项目堆成“功能清单”。参考关系分三层：

1. **产品底座参考**：芋道、Element Plus、Moodle、Open edX 证明课程管理、后台工作台、权限治理和 LMS 生态成熟。
2. **软件工程学习证据参考**：GitHub Classroom、PrairieLearn 证明自动测试、作业反馈和代码类学习活动可以成为教育证据。
3. **智能体治理参考**：LangGraph、OpenTelemetry GenAI 证明状态化 Agent、人机协同和 GenAI 可观测是可上线智能体的重要工程趋势。

SE-Path 的原创断点在于：把这些底座能力统一进“软件工程学习增值闭环”，而不是复制它们的产品边界。

| Vue 组件库 | Element Plus | https://github.com/element-plus/element-plus | Vue3 UI 组件、表格、表单、步骤、抽屉等 | 它只提供组件，不提供教育业务闭环 | 用 Element Plus 实现可上线的教师工作台交互 |
| LMS 平台 | Moodle | https://github.com/moodle/moodle | 课程、班级、作业、插件生态和开源 LMS | LMS 管课程，不理解 PR/CI/Review 过程证据 | SE-Path 可作为软件工程课程的学习路径伴学层 |
| LMS 平台 | Open edX | https://github.com/openedx/openedx-platform | 大规模课程创作与交付、LMS/CMS/MFE 架构 | 偏在线课程平台，不天然处理项目式开发证据 | SE-Path 聚焦项目交付过程中的诊断与干预 |
| 编程课程作业 | GitHub Classroom | https://docs.github.com/en/education/manage-coursework-with-github-classroom/teach-with-github-classroom/use-autograding | 作业仓库、push 后自动测试、学生即时反馈 | 自动测试能看结果，但不形成增值诊断和教师复核闭环 | 把 PR/CI 失败转成 EvidenceEvent、Safe-VOI 行动和反思记忆 |
| 在线评测 | PrairieLearn | https://docs.prairielearn.com/ | 参数化题目、自动评分、实时反馈 | 强在题目和测评，不直接覆盖工程项目协作过程 | 从“做题反馈”扩展到“工程能力节点与路径状态” |
| Agent 编排 | LangGraph | https://github.com/langchain-ai/langgraph | 状态化 Agent、持久执行、人机协同 | 只是通用编排运行时，不自带教育证据模型 | SE-Path 把人机协同固定为教师发布门和证据账本 |
| GenAI 可观测 | OpenTelemetry GenAI | https://github.com/open-telemetry/semantic-conventions-genai | GenAI spans、metrics、events 和工具调用观测语义 | 它是观测标准，不给学习诊断逻辑 | 后续把 LLM trace 与 EvidenceEvent 合并做教学审计 |

## 5. 竞争差异

| 对比对象 | 对方优势 | 评委可能质疑 | SE-Path 回答 |
|---|---|---|---|
| 通用 AI 答疑 | 回复快、覆盖广 | 是否只是接了大模型？ | SE-Path 的核心输入是工程证据流，输出是路径状态、脚手架、教师复核和反思记忆 |
| LMS 平台 | 课程管理成熟 | 是否要重做 Moodle/Open edX？ | 不做通用 LMS，只做软件工程项目式学习的伴学闭环，可作为外挂层接入 |
| 自动判题/自动评分 | 测试反馈明确 | 是否只是 CI 可视化？ | CI 失败只是入口，系统还做诊断、不确定性、Safe-VOI、教师发布门和学生反思 |
| IDE 编程助手 | 能直接帮写代码 | 学生会不会作弊？ | 直接答案请求进入安全门禁，只给检查清单、失败用例模板和反思提示 |
| Agent 编排 Demo | 多 Agent 看起来智能 | 是否缺少真实业务场景？ | 业务场景锁定 REST API、PR、CI、Review、Rubric 和教师复核，评委可按流程点击 |
| 数据看板 | 指标清楚 | 是否只会展示结果？ | SE-Path 同时能修改状态、写账本、导出 JSON、配置 Rubric 和推进学生回流 |

## 6. 商业化路径

### 6.1 首个切入场景

| 目标客户 | 典型痛点 | SE-Path 价值 |
|---|---|---|
| 高校软件工程课程 | 老师看不完 PR/CI/反思，难以及时发现学生真实短板 | 把班级失败 PR 转为教师工单队列，优先处理高风险和低证据学生 |
| 高职/产教融合课程 | 项目制教学需要过程证据，但平台多停留在提交结果 | 用证据账本证明学生如何定位、修复和复盘 |
| 企业新人训练营 | 新人代码评审、测试覆盖和异常处理能力差异大 | 把真实任务失败转为训练路径和导师复核工单 |

### 6.2 产品包

| 版本 | 适用对象 | 核心功能 | 交付方式 |
|---|---|---|---|
| 课程试点版 | 1-3 门课程 | 本地/私有部署、工单队列、增值诊断、证据账本、Rubric 配置 | 项目制课程试点 |
| 学院版 | 多班级、多教师 | 课程模板、教师协作、角色权限、班级周报、数据导出 | 接芋道后端与学校身份 |
| 产教融合版 | 校企训练营 | 企业任务模板、导师复核、训练路径、项目证据归档 | 私有化或专属租户 |

### 6.3 收费逻辑

| 收费项 | 说明 | 边界 |
|---|---|---|
| 课程试点服务费 | 帮助学校完成课程建模、Rubric 配置、首轮试点和报告 | 不承诺真实提分，只承诺试点数据与过程评估 |
| 学生席位费 | 按课程人数和使用周期收费 | 学生数据需要学校授权、脱敏和保留期限 |
| 私有化部署费 | 对接学校 SSO、Git/CI/LMS 和本地数据库 | 不把未授权生产数据接入提交包 |
| 企业训练营服务费 | 围绕岗位任务和新人代码审查流程配置 | 不做就业预测和人员淘汰决策 |

## 7. 评审答辩主线

### 7.1 30 秒版本

SE-Path 学伴把软件工程课程中的 PR、CI、Review、对话和反思转成 EvidenceEvent 证据账本，再用增值评价和 Safe-VOI 选择安全下一步。它不替学生写答案，不自动评价学生，而是让教师在芋道工作台中确认发布，并把学生补证据和反思回流到长期学习路径里。

### 7.2 90 秒版本

我们的作品面向软件工程项目式学习。这个场景和普通题库不同，学生的能力短板常常出现在 PR 失败、CI 日志、边界测试不足、Review 表达和复盘迁移中。

SE-Path v2 做成了芋道教师工作台：教师先看班级工单队列，再进入单个学生的增值诊断单。系统会说明当前能力、期望能力、差值、证据覆盖和不确定性。证据不足时不会强判，只提示补证据。

下一步由 Safe-VOI 策略选择，优先给低风险、高价值、可复核的脚手架行动。AI 不直接给完整代码，也不自动发布。教师可以批准脚手架、退回补证据或转人工会谈。

学生完成补证据和反思后，系统写入证据账本，阶段推进到闭环完成，并支持 JSON 导出。这个闭环已经通过本地自动化流程测试、构建和多端截图验收。

所以它不是聊天助手，而是把软件工程学习证据变成可治理、可复核、可持续优化的学习路径经营系统。

### 7.3 评委尖锐追问卡

| 追问 | 回答 | 可打开证据 |
|---|---|---|
| 你们是不是套了一个 AI 聊天壳？ | 不是。聊天只是证据来源之一，核心对象是 `LearningWorkOrder`、`EvidenceEvent`、`EvidenceLedgerEntry` 和 `TeacherDecision`。 | `src/types.ts`、证据账本抽屉 |
| AI 会不会直接帮学生写代码？ | 不会。直接答案请求进入安全门禁，页面文案和导出账本都写明只给检查清单、用例模板和反思提示。 | Safe-VOI 区、导出 JSON |
| 为什么用芋道？ | 赛题要做可上线智能体，芋道生态已有后台、RBAC、多租户、数据权限等工程底座；我们把教师工作台做成可迁移形态。 | 架构图 26、PPT 第 4-5 页 |
| 当前是不是只有前端？ | 当前 v2 用本地 mock API 和 localStorage 跑通闭环，已明确是第一版边界；后端 API 在设计中保留 WorkOrder、TeacherDecision、Ledger、Rubric 等对象。 | v2 设计方案、架构图 26 |
| 你们的算法创新在哪里？ | 在 Safe-VOI、增值评价、证据覆盖和教师发布门的组合：不是追求一次回答，而是控制下一步行动的价值、风险和可复核性。 | 算法图 28、PPT 第 7 页 |
| 如何证明不是静态页面？ | 页面支持工单筛选、教师决策、学生回流、账本导出、Rubric 配置；`npm run test:flow` 已覆盖关键流程。 | `design-qa.md`、flow test |
| 怎么商业化？ | 先切高校软件工程课程，再扩展高职产教融合和企业新人训练；收费来自试点服务、席位、私有化部署和训练营配置。 | 本文件第 6 节 |
| 如何保护学生权益？ | 系统只做形成性诊断，不排名、不惩罚、不就业预测；证据不足时标注不确定，教师确认后才发布。 | 页面边界声明、导出 JSON |

## 10. 边界声明

1. 当前 v2 Demo 使用本地 mock API 和 localStorage，证明产品闭环，不宣称已接入真实学校生产数据。
2. 所有增值评价均为形成性诊断，不做排名、不做惩罚、不做就业预测，也不作为毕业或其他高风险决策依据。
3. 开源项目仅作为设计参考或后续可替换底座，未在本材料中宣称完整集成。
4. 真实课程效果需要试点、授权、脱敏、教师标注和统计验证后才能声明。
5. AI 不自动给最终答案，不自动发布，不自动评价学生；教师确认是系统边界的一部分。
