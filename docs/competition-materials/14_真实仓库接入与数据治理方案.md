# 14 真实仓库接入与数据治理方案

本文档说明 SE-Path 学伴如何从比赛 Demo 扩展到真实软件工程课程仓库。目标是让评委看到：当前应用不是只能点击固定脚本，而是已经具备把 Issue、PR、CI、Review、反思等工程证据接入学习闭环的产品骨架。

## 一、已实现的接入沙箱

当前产品新增“仓库证据接入沙箱”面板，源码位置：

```text
sepath-cloud-app/src/engine/eventIngestion.ts
sepath-cloud-app/src/data/repositorySamples.ts
sepath-cloud-app/src/components/RepositoryImportPanel.tsx
sepath-sites-app/src/engine/eventIngestion.ts
sepath-sites-app/src/data/repositorySamples.ts
sepath-sites-app/src/components/RepositoryImportPanel.tsx
```

该面板支持：

- 将 Issue、PR、CI、Review、反思记录归一化为 `EvidenceEvent`。
- 在导入前执行质量门检查。
- 按事件 ID 自动去重，避免重复导入污染账本。
- 导入后自动触发学情诊断、路径规划、知识边界、算法验证、评审证据和上线就绪面板重算。

## 二、当前样本事件

当前合成样本模拟一个软件工程课程中的真实项目片段：

| 事件 | 来源 | 学习含义 |
| --- | --- | --- |
| Issue #42 | Git | 学生创建异常路径任务，但验收条件不完整 |
| PR #42 | Git | 学生提交测试与实现，但 PR 说明不足 |
| CI failed | CI | 库存不足场景期望 409，实际返回 500 |
| Teacher Review | 教师 | 要求先补验收表，禁止 AI 直接替写完整 service 代码 |
| CI passed | CI | 学生修复后测试通过 |
| Reflection | 学生 | 学生形成“先验收条件、再改代码”的迁移记忆 |

## 三、质量门

导入前系统检查五类质量门：

| 质量门 | 目的 |
| --- | --- |
| 事件结构 | 确认每条仓库信号包含 id、类型、来源、时间、标题、描述和能力影响 |
| 工程证据 | 确认同时包含 Git 和 CI 信号 |
| 人类反馈 | 确认包含教师 Review 或学生反思 |
| 隐私脱敏 | 拦截疑似邮箱和手机号 |
| 失败到修复闭环 | 确认既有 CI 失败，也有后续 CI 通过 |

## 四、真实平台接入路线

### 1. GitHub Classroom

建议优先接入：

- Issue created / edited
- Pull request opened / synchronized
- Pull request review submitted
- Check suite completed
- Workflow run completed

接入方式：

- 初赛 Demo：使用导出的 JSON 或 Webhook 样本文件。
- 决赛试点：使用 GitHub App 只读权限采集课程仓库事件。

### 2. Gitee / GitLab

国内课程场景可接入：

- Gitee Webhook
- GitLab Webhook
- 自建 Git 服务导出的提交记录

核心要求不是平台品牌，而是事件能归一化为统一的 `EvidenceEvent`。

### 3. CI 平台

可接入：

- GitHub Actions
- GitLab CI
- Gitee Go
- Jenkins
- 学校自建评测系统

最低可用字段：

- run id
- commit sha
- status
- failed test name
- failure summary
- completed timestamp

## 五、数据映射

| 外部字段 | EvidenceEvent 字段 |
| --- | --- |
| provider + repo + event id | `id` / `traceId` |
| event kind | `type` |
| event timestamp | `timestamp` |
| actor | `actor` |
| provider type | `source` |
| title | `title` |
| body / log summary | `detail` |
| rubric mapping | `competencyImpacts` |
| confidence score | `confidence` |
| risk policy | `risk` |

## 六、权限与隐私

真实接入时必须坚持：

- 只读采集。
- 最小权限。
- 不采集学生手机号、邮箱、身份证号等非教学必要信息。
- 学生身份使用脱敏 ID。
- 教师可查看原始证据摘要，但学生互相不可查看隐私信息。
- 导出账本默认脱敏。
- 高风险建议不自动发布给学生。

## 七、为什么这个能力能拉开比赛差距

普通伴学 Demo 往往只展示对话能力。SE-Path 学伴把软件工程课程天然存在的工程过程证据纳入智能体：

- PR 失败不是失败，而是学情诊断证据。
- CI 日志不是噪声，而是能力画像更新信号。
- Review 不是评语，而是教师复核与治理事件。
- 反思不是作文，而是长期记忆和迁移学习证据。
- 导入、诊断、推荐、复核、反思、导出账本构成闭环。

这使作品更像真实可落地的软件工程课程智能运营系统，而不是一个一次性演示页面。

## 八、下一步真实试点

建议下一阶段按以下顺序推进：

1. 选择 1 个真实课程仓库。
2. 导出最近 10 条 Issue、PR、CI 和 Review 记录。
3. 使用 `eventIngestion.ts` 先做离线 JSON 归一化。
4. 与教师一起标注每条事件影响的能力维度。
5. 运行 Demo 并比较系统诊断与教师判断。
6. 再决定是否接入 Webhook 或 GitHub App。

这样可以低风险地从比赛 Demo 过渡到真实教学试点。
